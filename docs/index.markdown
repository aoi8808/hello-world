# これまでに学んだソフトウェア工学の内容（第1回〜13回）

## 第1回
**到達目標:** ソフトウェア・エンジニアリングの基礎知識を理解し、実務的なスキルを習得すること
**講義の狙い:** ソフトウェア工学の知見について自ら考える機会を得ること
### ソフトウェア工学の難しさ ###
ソフトウェア工学の学習や実践には、主に以下の3つの難しさがある。
**実務経験の必要性:**現場の実務から体系化された知識であるため、実際にソフトウェア開発に携わった経験がないとイメージが湧きにくい。
**知見と実践の乖離:** 知識として理解できたとしても、それを実際の開発現場で実践することは難しい。
チーム全体での共有: 個々人がソフトウェア工学の知識を持っているだけでは不十分であり、チーム全体で知見を共有して取り組む必要がある。

## 第2回
### ソフトウェアの特徴と定義 ###
ソフトウェアは、実行によって必要な特性や機能を提供するプログラム、適切に情報を扱うためのデータ構造、および使用法などを記した情報から構成される。
ハードウェアと異なり物理的に劣化することはないが、悪化はする。
新しい環境やビジネス要求に適応し、他システムとの相互運用や再構築に向けて進化・拡張し続ける必要がある。

### ソフトウェア工学の目的と本質 ###
ソフトウェア工学とは、ソフトウェアの開発、運用、メンテナンスに対してシステマティックで定量化可能なエンジニアリング手法を適用することである。
変化し続ける状況に対応し、旧システムとの互換性や他システムとの相互運用性を保ちながらシステムを進化させる方法論の構築を目標とする。
最終的には「品質」「コスト」「納期」の最適なバランスを実現するための手法である。
課題解決（プラクティスの本質）のステップは、「問題を理解する（分析）」「解決策を計画する（設計）」「実行に移す（実装）」「結果が正しいことを理解する（テスト）」の4段階からなる。

### 3. Hookerの7原則
ソフトウェア開発において意識すべき7つの原則
1. ユーザーに価値を提供することがシステムが存在する唯一の理由である。
2. 設計は可能な限りシンプルに保つべきである。
3. プロジェクト成功には明確なビジョンを持ち続けることが不可欠である。
4. 他者が利用・理解することを常に念頭に置いて仕様決定や実装を行うべきである。
5. 未来の仕様変更に備え、多くの選択肢を残せるようオープンな設計にする。
6. コスト低減と価値向上のため、再利用に先駆けて計画する。
7. 行動を起こす前に、簡潔明瞭に考えることがよい結果を生む。

## 第3回
### ソフトウェアのライフサイクル ###
ソフトウェアのライフサイクルは、ビジネスやシステム上のニーズが発生し、要件定義などの企画・計画を行う「誕生」の段階から始まる。その後、実際の開発を経て実稼働や保守運用を行う「開発・運用」の段階へと移行し、最終的にはサービスの終了や新規ソフトウェアへのリニューアルを伴う「廃止」へと至る。
### 要件定義 ###
要件定義では、システムの目的や機能、システム構成、目標性能などを明確に定めます。実現する機能としない機能を明確に切り分け、実現性評価を通じて機能の絞り込みや代替策の検討を行うことが重要である。また、要件定義書はプロジェクト関係者間でスコープを共有するためのバイブルとなるほか、社内外への協力依頼や、外部ベンダーに対する提案依頼書（RFP）としても機能する。
### 設計工程 ###
設計工程では、要件定義書をもとに、クラスやモジュールといったコーディングが可能なレベルの仕様書へと落とし込み、WBS（作業分解構成図）を作成。続く制作工程では、設計書に従ってシステムの構築を行う。制作は自社開発（内製）だけでなく、外部への委託（調達）も行われる。
テストおよびデバッグの工程では、「バグのないソフトウェアはない」という前提に立ち、バグの早期発見と対処を目指す。しかし、すべてのテストを行うことは工数的に不可能であるため、テストの範囲や深さを適切に見極める必要がある。
###　運用・保守　###
の段階では、稼働後のデータをプロアクティブに活用することが求められる。システムの故障率は、初期故障、安定稼働、摩耗故障と推移する「バスタブ曲線」を描く傾向があり、ソフトウェア以外の要因や当時の開発担当者がすでにプロジェクトから離れている可能性も考慮しなければならない。

## 第4回 ##
###　プロジェクトと計画手法　###
プロジェクトとは、必ず終わりがある「有期性」と、独自の目的を達成する「独自性」を持つ仕事であり、通常のルーティンワークとは異なる。目標に向かう計画手法には、現在の立ち位置から順に進めていく「フォアキャスティング」と、定めた明確な目標から逆算して必要なプロセスを計画する「バックキャスティング」がある。不確実性の高いプロジェクト業務においては、バックキャスティングの手法が適している。

### ソフトウェア分析と評価 ###
ソフトウェアを見える化するためには、「品質（Quality）」「コスト（Cost）」「納期（Delivery）」のQCDを分析し、システム要件に応じて優先度を決定する。ソフトウェアの価値を測る評価指標としては、コードの物量（ステップ数やオブジェクト容量）のほか、要件からシステム規模や原価を概算するファンクションポイント（FP）法、視認性や操作性などの「使い勝手」がある。品質管理においては「バグのないソフトウェアはない」という前提（Hyrumの法則）に立ち、バグ発生率などを指標としてテストの妥当性やリリースのタイミングを判断する。

### 開発プロセス###
開発プロセスには複数の手法が存在する。要件定義から順次工程を進め、進捗管理が容易な「ウォーターフォール型」、プロトタイプの作成と評価を繰り返す「スパイラルモデル」、機能を分割して段階的に完成させる「反復型」、そして仕様変更を許容し、動くソフトウェアの早期提供と顧客との協調を最優先する「アジャイルプロセス」がある。アジャイルの中には、スクラムやカンバン、XP（eXtreme Programming）などの具体的な実践手法や、開発と運用を連携させるDevOpsの考え方が含まれる。

### 開発プロセスの選定とリスク管理 ###
どの開発手法を採用するかは、プロジェクトの規模、要求される品質や納期、採用する技術、そして開発メンバーのスキルや顧客の性質を総合的に評価して決定する。また、人的・技術的課題から、ニーズの変化、さらには天災やメンバーの病気といった予測不可能な事象に至るまで、想定されるリスクをあらかじめ把握して対処する「リスク駆動型」の視点を持つことが重要である。

## 第5,6回
### WBS（Work Breakdown Structure）の概要 ###
WBSとは、プロジェクトの目標を達成し必要な成果物を作成するために、チームが実行する作業を階層的に分解した構成図のことである。プロジェクト全体を細かなタスクに分解して作業順に並べることで、スコープが明確になる。さらに、全体管理や作業計画も可視化されるため、実際のプロジェクト進行時にはこのWBSに則って作業を実行していく。

### WBSの作成手順 ###
WBSを作成する際は、まずバックキャスティングやトップダウンのアプローチを用いてプロジェクトのスコープを明確にすることから始める。次に、大きな作業単位でタスクをグルーピングし、それぞれの作業がどの順番で行われるべきかという相互関連を整理する。最後に、各グループに含まれる具体的な作業を、漏れなくダブりなく洗い出すことが重要。

## 第7,8回：コーディング
### リーダブルコードの重要性 ###
ソフトウェア開発において、コードは「書く時間よりも読まれる時間の方が圧倒的に長い」という特性がある。そのため、他人はもちろん、未来の自分が読んでも意図が伝わる「読みやすいコード（リーダブルコード）」を書くことが不可欠である。この目的を達成するためには、プロジェクト全体で統一されたコーディングのルール（スタイルガイド）を設ける必要がある。

### Pythonのスタイルガイド（PEP8） ###
Pythonにおける代表的なコーディング規約がPEP8である。コードの可読性を高めるための具体的なルールとして、1行の長さを79文字以内に抑えることや、インデントにはタブではなく4つのスペースを使用すること、演算子の前後に適切なスペースを配置することなどが定められている。また、変数や関数名には小文字とアンダースコア（スネークケース）、クラス名には単語の先頭を大文字にする（キャメルケース／CapWords）といった命名規則を遵守し、UTF-8エンコーディングとASCII文字を基本とすることが推奨される。

### 静的コード解析ツール（Linter）の活用 ###
設定したコーディングルール（PEP8など）にコードが準拠しているかを自動的に検査するためには、「flake8」や「pylint」といったLinterと呼ばれる静的コード解析ツールを導入する。これにより、人間が目視で確認する手間を省き、構文エラー（Syntax Error）やスタイルエラーを機械的に検知して修正することが可能となる。

## 第9,10回：バージョン管理(1)
### Gitの基礎とコマンド学習 ###
ソフトウェア開発において不可欠なバージョン管理システムであるGitについて、基本的なコマンドや概念を実践的に学習する。具体的には学習サイト（Learning git branching等）を活用し、Gitのコミットの基本的な仕組みから、HEADの分離、コードの特定のコミットを取り込むcherry-pickやrebaseといった発展的な操作までを視覚的に学んだ。同時に、複数人での開発において重要となるリモートリポジトリの操作として、Clone、Push、Pullなどのコマンドについても理解を深め、ローカル環境とリモート環境を連携させる手法を習得した。

## 第11回：バージョン管理(2)
### GitHubの仕組みと基本操作 ###
リモートリポジトリのホスティングサービスであり、オープンソースソフトウェアの主要なポータルサイトであるGitHubの活用方法を学んだ。GitHub上での開発においては、他者のリポジトリを自分のアカウントに複製するフォーク（fork）や、それを手元のローカル環境にダウンロードするクローン（clone）といった操作が基本となる。また、テンプレートとして用意されたリポジトリをベースにして、新しいプロジェクトを効率的に立ち上げることも可能であった。

### プロジェクト管理機能とマークダウン ###
開発を円滑に進めるための管理機能として、バグの報告や機能追加の要望、タスクなどをチケット単位で管理するIssue（イシュー）機能が備わっている。さらに、これらのIssueをカンバンボードのような形式で視覚的に一覧化し、進捗状況をチーム全体で把握するためのProjects機能も活用される。ドキュメントの記述には、文章を簡単に構造化して書くことができるマークダウン（Markdown）記法が標準的に用いられており、必要に応じて様々なファイル形式（PDFやHTMLなど）に変換して利用される。

### 開発フローの実践（Codespacesの活用） ###
実際の開発や演習においては、ブラウザ上でVisual Studio Codeと同等のエディタ環境を構築できるCodespacesを利用する。この環境内で新しいブランチを作成し、ファイルの作成や更新を行ってコミットを記録する。その後、変更履歴をGitHubのリモートリポジトリへプッシュし、本流のブランチへ変更内容の取り込みを提案するPull Request（プルリクエスト）を作成し、最終的にマージ（統合）して反映させるという、一連のGitHubフローを実践的に習得する。

## 第12回：CI/CD
### 継続的インテグレーション（CI）と継続的デリバリー（CD） ###
CI（Continuous Integration）とは、コードの変更を共有リポジトリに頻繁に統合し、その都度「自動テスト」と「ビルド」を定期的に実行することで、バグの早期発見と修正を可能にするプロセスのことである。一方、CD（Continuous Delivery）は、CIを通過したコードをテスト環境や本番環境へ自動的にデプロイ（配置）するプロセスのことである。これらCI/CDのパイプラインを構築することで、手動操作によるミスを排除し、ユーザーへの迅速な価値提供とスムーズな開発進行が実現される。

### GitHub ActionsによるCI/CDの実践 ###
GitHubでは「GitHub Actions」という機能を用いてCI/CDを簡単に構築できる。リポジトリ内の `.github/workflows/` ディレクトリにYAML（`.yml`）形式の設定ファイルを配置し、「どのようなイベント（PushやPull Requestなど）をトリガーとして」「どのような環境で」「どのような手順（ジョブやステップ）を実行するか」を定義する。例えば、Pull Requestが作成された際に自動で前述のLinter（flake8）を走らせ、文法チェックのレポートを自動生成させるといったワークフローが実現できる。

## 第13回：CI/CDの実践（GitHub Pages）
### GitHub PagesとJekyllの活用 ###
GitHubには、リポジトリに保存されたファイルをそのままウェブページとして公開できる「GitHub Pages」という機能があり、この機能の背後にもCI/CDの仕組みが動いており、ユーザーがMarkdownファイルなどをPushすると、自動でビルドが行われてウェブサイトが更新される。さらに、静的サイトジェネレーターである「Jekyll（ジキル）」を組み合わせることで、開発者は複雑なHTMLを書くことなく、簡単なMarkdownファイルを記述するだけで見栄えの良いウェブサイトを自動生成することができる。

### ウェブサイト公開のワークフロー ###
GitHub Pagesを利用するためには、リポジトリ名を特定の形式に設定し、設定画面から公開元ブランチを指定する。そして、ウェブサイトの設定を記述した `_config.yml` ファイルや、トップページとなる `index.markdown` などのファイルを作成し、GitHubにPushする。この一連の作業にもGitHubフローを適用し、作業ブランチで変更を行った後にPull Requestを作成し、マージすることで、変更内容がCIパイプラインを経由して安全に本番環境のウェブページにデプロイされる仕組みを学んだ。
